# 后端响应与生图等待优化方案

日期：2026-10-27（Asia/Shanghai）。审计基线：`main / e9f41c6`，产品 `0.2.9`。
状态：owner 已于 2026-10-27 明确选择 GitHub 版本并授权优化；F-076 实现、独立审查及本地验收完成，未发布。

## 背景与目标

owner 要求全面优化后端响应速度、减少延迟，重点让用户最快拿到生图结果；已明确目标为约 **10 个同时进行的生图任务**。

按全站约 10 单、单 worker 部署设计；这不等于修改单用户 system 并发额度或同会话提交限制。保持模型 `gpt-image-2`、画质、计费、鉴权及已有产品行为。少量前端状态接收改动是为了让后端完成后能立即显示图片，不涉及视觉改版。

端到端时间拆为：提交入队 + 队列等待 + 上游处理/传输 + 图片持久化 + 结算提交 + 客户端发现/图片加载。核心目标是去掉本站额外等待；上游真实生成时间需要相同参数的独立实测。

## 方案比较

| 方案 | 优点 | 限制 | 选择 |
| --- | --- | --- | --- |
| 仅调整并发/轮询参数 | 改动少 | 保留批次屏障；加快轮询增加数据库流量；无法解决异常退出 | 不足以满足目标 |
| 保留 PostgreSQL，分批优化调度、通知与查询 | 能直接处理已找到的等待；沿用持久队列和资金事务 | 需要队列竞争、故障、浏览器回归测试 | **推荐** |
| 引入 Redis 队列并拆分服务 | 更大规模下可独立扩容 | 增加状态同步和运维成本，对 10 单规模尚无必要 | 不纳入本次 |

## 改造设计与顺序

### 第一批：持续补位、可靠执行、结果立即可用

1. 用有界、持续补位的调度器替换整批 `Promise.all` 屏障。上限可配置；本项目目标配置为单 worker 10 槽。每次只领取当前有空位能立即执行的任务。按创建时间选择排队任务，慢任务不阻止其他槽补位。
2. PostgreSQL 使用单条 CTE/短事务完成 `FOR UPDATE SKIP LOCKED` 选取和状态更新，提交后再发上游请求；绝不在图片生成期间持有队列行锁。原有按 ID 调用入口也必须通过统一抢占规则，不能产生绕过抢占的公开执行接口。Neon 可选驱动保留兼容路径并覆盖测试。
3. 只允许一个 worker 实例承载本次 10 槽配置；配置与部署说明明确并发是每进程值。`SKIP LOCKED` 防重复领取，不提供全站并发上限；未来多实例部署需要另加全局容量协调。旧 running 任务不能在崩溃恢复时无条件重入队，避免重复上游下单。
4. 隔离单任务异常；队列读取失败采用有界退避，终止信号停止接新任务并排空在途任务。监控写入失败不杀掉消费者；结算失败必须回滚并如实反映，不能吞错并报告成功。custom 凭据清理失败要有脱敏告警及现有清理兜底。
5. 参考图读取、结果下载及上传遵守任务剩余时间，支持底层取消；无取消能力的本地操作要采取有界处理和迟到结果检查。迟到文件不能覆盖已发布文件或把 failed 改成 succeeded；失败不扣费，孤儿图沿用清理机制。
6. 成功状态协议补齐图片 ID、保存状态等前端必要字段，将已提交的终态直接合并到当前会话缓存，再后台刷新余额/资产/详情；不再等待第二次详情请求才能看到图片。不可用旧的 running/queued 响应覆盖终态。
7. 补充分段指标：入队耗时、queue wait、claim、relay、存储、结算、端到端完成；只记录任务标识、阶段、时长与归一化结果，不记录 Key、提示词、图片字节或上游敏感原文。

### 第二批：即时通知与常用读接口优化

1. PostgreSQL `LISTEN/NOTIFY` 作为提示信号：入队/状态变化事务提交后唤醒消费者和 Web。通知不作为持久任务或状态真相源；专用监听连接启动/重连后重新读库，保留轮询回扫，丢通知不丢任务。它主要减少空闲时 0–500ms 的扫描等待。
2. 增加经过用户鉴权的 SSE 状态通道，推送已提交的任务状态；Web 进程共享数据库监听器，不给每个浏览器占一个数据库连接。连接首次建立/重连读取权威快照；心跳、连接回收、事件去重和乱序保护齐全；连接失效回退现有批量轮询。用户断开浏览器不会取消生图。验证代理不缓冲 SSE，并在鉴权过期时断开重新认证。
3. SSE 按 owner 范围分发，每次发布前有服务端归属约束；不发送 custom Key、临时上游地址或未结算成功结果。只在有在途任务时保持必要订阅。此项降低完成后的发现延迟，不改变模型推理时间。
4. 默认侧栏不再读取旧会话列表；搜索时启用原搜索接口。保持乐观插入、项目分组及排序行为。
5. 合并 `loadMe` 的独立查询，保留返回字段和实时价格语义；列表查询按连接池指标选择合并/并行，不对金额、余额、封禁及价格引入跨请求 TTL 缓存。
6. 单项目写后定向读取；项目/会话排序用批量 SQL 替代逐条 UPDATE，保留事务、owner 限制和完整 ID 集合校验。资产列表统一参数上限与错误行为。
7. 在隔离测试库用代表性数据核对查询计划，补通知 user/time 索引、队列领取索引；其他索引仅在计划支持时增加。后台队列统计先过滤 active 状态，避免为数几个排队任务扫描全历史。
8. 为读/事务/auth 池记录获取连接时间、等待数与 SQL 耗时，容量配置化但不直接从 4 一律改 10。10 个远程生成请求不需要各自持有数据库连接。

两部分按独立文件范围并行实现，先分别验证，再统一做资金/协议/浏览器集成回归；因为状态协议与直接显示联动，最终作为一个性能功能提交。实施计划见 `docs/superpowers/plans/2026-10-27-backend-performance.md`。

### 后续可选：上游与大历史数据

- 固定同一模型、提示词、画质、尺寸，测当前 Relay 的单单和 10 并发 p50/p95、限流率、首字节/完整响应时间，确认它能实际并行接受任务。若上游串行排队，本站并发池无法消除该瓶颈。
- 测部署区域到 Relay 与用户的网络路径，按实测选择网络/供应商优化；本方案不迁移服务器或更换用户 Key 的目标地址。
- 极速草稿、较低画质、JPEG 输出是可选产品模式，不改变现有默认。当前存储假定 PNG，要先兼容 MIME、扩展名、尺寸读取和透明背景要求，不能只改上游参数。
- 流式部分图片不纳入当前承诺：官方 `gpt-image-2` 模型页目前标注 Streaming Not supported；通用图像指南的流式能力不能直接推定适用于当前 Relay。只有确认提供方能力和成本后另行设计预览。SSE 完成通知不依赖上游流式能力。
- 项目折叠懒加载、长会话历史游标分页、搜索 trigram、后台汇总缓存另开具体子任务，以免破坏当前“整组会话排序”的契约。

## 明确不做什么

- 不改积分定价、成功后扣费、FIFO、账户锁、generation_id 幂等、余额非负或 custom 零扣费/不回退规则。
- 不通过先宣告成功、跳过图片持久化或放松鉴权换取表面提速。
- 不减少默认画质、不换模型、不发同一任务的多供应商竞速请求、不在结果未知时盲目重试上游。
- 不增加 Redis/Kafka/微服务，不扩大单用户业务额度，不修改现有 5 分钟端到端超时定义。
- 不进行生产发布、线上数据库迁移或服务器配置修改；真实 Relay 验证需有合适的测试 Key 与受控调用。

## 验收步骤

1. 先创建独立 `.env.test` 和 disposable 测试库，严格与 `.env` 本地开发库分开；用固定耗时假 Relay，不消耗真实费用。
2. 错峰入队：一单未完成时新增九单，九单应填入空槽；10 单中一单完成，第 11 单立即补位，不等其他九单；确认在途调用不超过配置上限。
3. 多消费者竞争同一任务，上游只调用一次；注入扫描/claim/监控异常，其他任务继续；崩溃后 running 不被盲目重复提交。
4. 超时/存储失败/迟到响应与 scheduler、结算同时发生：失败不扣、成功最多一次扣费、无负余额；custom 账本不变、凭据按终态清理。
5. 完成状态直接进入缓存，图片可显示而无需阻塞等待详情请求；并行任务、续聊、编辑、页面切换都不丢乐观状态。
6. LISTEN/SSE 断线、漏通知、重复/乱序事件、重连、用户退出和跨用户访问均有覆盖；回退轮询能恢复权威状态。
7. 10 并发下用相同机器、相同夹具、相同假 Relay 延迟作改造前后对照，记录端到端各阶段的 p50/p95、错误率、SQL 次数、连接池等待及响应体积。目标：有空槽时新任务开始 p95 < 500ms；SSE 正常时从成功事务提交到浏览器呈现图片元素 p95 < 500ms（不含远程图片下载/解码）；这些是验收目标，尚非已达到的数字。
8. 用代表性历史量验证 API 查询计划；常用读取错误率为 0、p95 不劣化，确认被删的重复 SQL 和串行详情请求确实不再发生。金额精度与实时配置语义不变。

## 风险与依据

- 现有 5 分钟 deadline 从入队起算，排队会侵占上游时间；本次减少排队，不靠无上限延长时间隐藏容量问题。
- 通知是加速信号，DB 是唯一真相源；所有对用户显示的成功状态都必须在持久化和结算提交之后。
- 上游 Key 并发/速率、服务器 CPU/内存/带宽、图片尺寸影响容量；不承诺固定百分比或秒数，不把本地空库测量外推到线上。
- PostgreSQL 官方说明：[SKIP LOCKED 用于多消费者队列表](https://www.postgresql.org/docs/17/sql-select.html)、[NOTIFY 在事务提交后交付](https://www.postgresql.org/docs/17/sql-notify.html)。
- OpenAI 官方说明：[gpt-image-2 模型能力](https://developers.openai.com/api/docs/models/gpt-image-2)、[图像生成参数与延迟取舍](https://developers.openai.com/api/docs/guides/image-generation)。当前项目连接第三方 Relay，实际兼容性仍需单独验证。
