# 协作流程规范

> 本文是"人 + AI"开发本项目的操作手册：什么时候开会话、怎么干活、
> 怎么收工、翻车了怎么办。每条规则都标注了出处（Anthropic 工程博客）。

---

## 一、开会话：什么粒度开一个新会话

**规则：一条功能 / 一个 bug = 一个会话。** 别把不相关的事塞进同
一个会话。

- 出处：《Effective Harnesses for Long-Running Agents》——一次只做
  一条功能，防 AI "一口吃成胖子"失控；《Claude Code Best Practices》
  ——"kitchen sink session"（大杂烩会话）是典型失败模式。
- 开新会话的信号：
  - 上一条功能验收全绿、已 git 提交 → 关会话，开新的
  - 同一个问题纠正 AI **两次还不对** → 关会话，把教训写进更具体的
    新 prompt 重开（出处：Best Practices "correcting over and over"）
  - 会话里话题开始漂移 → 立即开新会话
- 新会话开始后，AI 会先执行 CLAUDE.md 的"会话开始 SOP"（读进度、
  看清单、跑 typecheck 确认基线是绿的），**等它走完 SOP 再布置任务**。

## 二、干活中：先对齐"合同"再动手

**规则：AI 动手前必须先复述"要做什么 + 怎么算做完"，你点头后才能
写代码。**

- 出处：《Harness Design for Long-Running Application Development》
  的 sprint contract——先协商"done 长什么样"，再写代码。
- 标准开场白（直接抄）：
  > 我要做 <任务>。先别写代码：复述你要改哪些文件、按
  > docs/FEATURES.md 哪条验收、跑哪些 VERIFY.md 命令。我确认后你再动手。
- 较大新功能：先让 AI 在 `tasks/` 按 TEMPLATE.md 建任务卡，你确认
  任务卡后再开干。

## 三、关会话：四步收工，缺一不可

每次会话结束前，AI 必须依次完成：

1. **验收**：按 docs/VERIFY.md 跑对应命令，贴输出原文，全绿才算过。
2. **更新账本**：改 docs/FEATURES.md 对应条目状态（只许改状态）。
3. **写交接**：在 docs/PROGRESS.md 会话日志顶部追加固定格式条目。
4. **git 提交**：一条功能一次提交，信息格式
   `feat|fix: [F-编号] 一句话说明`。

- 出处：《Effective Harnesses for Long-Running Agents》——每次会话
  结束必须留下"干净状态"（可合并、有文档、下个会话能直接开工），
  交接靠 progress file + git history 双保险。

## 四、挑刺会话：每个重要功能完成后做一次

**规则：功能验收通过后，另开一个新会话专门挑毛病。**

- 标准开场白（直接抄）：
  > 以挑刺为目的评审 <功能> 的实现：对照 tasks/<任务卡> 和
  > docs/FEATURES.md 的验收步骤逐条核对，只报告影响功能正确性、
  > 安全和资金规则的问题，不报代码风格偏好。列出问题清单，不要修改代码。
- 拿到问题清单后，回干活会话（或再开一个修复会话）逐条修。
- 出处：《Harness Design》——干活的 AI 给自己的作品打分必然偏高，
  评审者要用**全新会话**（没有自我偏爱）；且必须限定"只报正确性
  问题"，否则会被带着过度修改。
- 什么算"重要功能"：涉及钱、登录安全、数据删除的必做；纯 UI 微调可跳过。

## 五、翻车救命卡：回滚到上一个正常版本

因为遵守了"一功能一提交"，你的 git 历史就是一串**已知正常的存档点**。
翻车了按下面做（命令让 AI 跑，你看着）：

1. **找存档点**：让 AI 跑 `git log --oneline -20`，你从上往下找
   最近一次"验收全绿"的提交。
2. **未提交的改动不要了**：`git restore .`（丢弃当前未提交修改）。
3. **整个回到存档点**：`git reset --hard <提交短哈希>`。
   ⚠️ 这会丢弃该提交之后的所有改动，AI 执行前必须向你确认。
4. **只想撤销某一个坏提交、保留其后正常提交**：用
   `git revert <坏提交短哈希>`（更安全，不丢历史）。
5. 回滚后必须重新跑 VERIFY.md 最低门槛两条命令，确认绿了再继续。

- 出处：《Effective Harnesses》——进度交接 + git 历史让 AI 能
  "恢复可用状态"，而不是猜哪里坏了。

---

## 附：你（owner）每次只需要做的三件事

1. 开会话时：发任务 + 等 AI 复述合同，点头或打回。
2. 收工时：看 VERIFY.md 红绿灯证据 + PROGRESS.md 新日志。
3. 定期（建议每周或每个大功能后）：确认 FEATURES.md 状态与
   实际产品一致——它是唯一的"功能真相账本"。
